# CLAUDE.md — Design System

## What This Is

A React component library + design system + documentation website. It has three interconnected parts:

1. **Component Library** (`/src`) — React components built with Vite + TypeScript, published to npm as **`rift-ds`**. Each component has its own folder with implementation, scoped CSS, and Storybook stories. The website is an npm-workspace consumer: it depends on the package by name and imports through the same `exports` subpaths any consumer would (the in-repo exports point at `./src`, so it's live source — see **Registries** below for the generated barrel/exports surfaces). The official component list and count live in `src/components/registry.json`; never hardcode a count.
2. **Documentation Website** (`/website`) — A separate Next.js app that showcases every component with live, interactive examples. Each component has its own page under `website/src/app/components/[component-name]/`.
3. **AI Layer** (spans both) — the site answering questions about itself: the library's `ai` component category, **the chat widget** (`rift-ds/chat` — the package's fourth kind of thing, between the components and the templates, and its only widget: `ChatWidget`, `ChatProvider` and `ChatLauncher` over the `useChat` engine, the fetch and scripted transports, the thread lifecycle and the `ChatEvent` protocol, with the server half in `rift-ds/chat/server`, the Upstash guardrails in `rift-ds/chat/upstash` and a scripted demo in `rift-ds/chat/demo`; `src/chat/registry.json` is its registry and the **Chat widget** row under **Registries** owns the details), the site-wide chat built on it (`SiteChatProvider` and `SiteChatMount` in `website/src/components/SiteChat/`, the site's thin configuration of the package: its routes, starters, model allowlist and privacy link), the Claude-backed `/api/chat` route — the package's `createChatHandler` configured with the persona, the corpus and the allowlist in `website/src/lib/chat-model.ts`, resolving the composer's model pick through a budget tier the guardrails compute from the day's spend, so the dearer model locks near the cap; the default is already the cheaper one, which leaves the step-down tier with nothing to change today — `/api/chat/followups`, which writes the suggestion chips under a finished answer with a smaller model, and `/api/chat/feedback`, which stores a visitor's thumbs verdict in Redis — rate-limited by the shared guardrails, disclosed on /privacy), the build-generated site corpus it reads (see the corpus rows and security boundary in **Registries** below) plus two deterministic lookup tools the model carries for what the corpus deliberately omits — the component prop API and the token registry — implemented once in `website/src/lib/site-tools.ts` and shared with the MCP endpoint, bounded by the route's tool loop (`maxModelCalls`) and surfaced to visitors only as trace points, plus the package's opt-in `ask_user` tool (`askUser` on `createChatHandler`, switched on by the route), through which a reply can end in a question with answers to pick: the set is sanitised by `src/chat/questions.ts` on both sides of the wire and drawn as a `QuestionCard`, asking ends the exchange with no further model call, and a turn that asks gets no follow-up chips, the answer-quality eval in `evals/chat`, and `/api/mcp` — a public, auth-free Model Context Protocol endpoint (stateless Streamable HTTP via `mcp-handler`) whose deterministic tools serve the component prop API, the registries, install setup, and corpus search to any MCP client. It calls no model, so the chat's guardrails deliberately do not apply — and it is unmetered by choice (no auth, no rate limit): the tools are cheap in-memory reads, and that decision is recorded in the route's doc block, to revisit if a tool ever stops being one. Its security boundary is the corpus rule inherited whole — every tool reads only generated, already-published data. Advertised in llms.txt; the tool count stated on /overview is held to the route's actual registrations by `scripts/validate-mcp-tools.mjs` (which also holds the display roster in `website/src/lib/mcp-tools.ts` — blurbs and example prompts, rendered by the landing page and get-started — to the registrations in both directions). The same generated data also ships as three file surfaces for agents, the per-component prop markdown, the agent starter (`/AGENTS.md`, one short file for an agent with nothing installed, shown in full on get-started) and the consumer agent skills (the library, applying a theme to existing screens, and auditing styles against the tokens), with a one-command installer for the latter (`npx rift-ds init`, the package's only bin, which reads the list of skills from a manifest on the site; three scaffold subcommands ride beside it, `npx rift-ds init app`, which writes the root wrapper (Next's `Link` into `LinkProvider`), the colour-mode script component and the base theme's font through `next/font`, and prints the whole root layout to use (the get-started page shows the same layout, held to the bin's output by `validate-chat-widget.mjs`), `npx rift-ds init chat`, which scaffolds the chat widget's routes, mount and env example, and `npx rift-ds init block <name>`, which copies in a block, a whole starting page built from the library (see the Blocks row under **Registries**), each from templates shipped beside the bin in `src/cli/templates/<subcommand>/` (`blocks/` for the last), never overwriting a file) — see their paragraphs under **Registries**.

**Every chat suggestion is one chip, and a chip never wraps.** Conversation starters, follow-up questions, and the FAB summary panel's chips share the same row component, so they share one length budget: `SUGGESTION_MAX_CHARS` in `src/chat/suggestions.ts` (the package's, so every consumer's chat holds the same line), set to what fits the message column on a small phone, where the panel fills the viewport. It is enforced at every point a suggestion enters the UI — the generator is told the number, the route drops a long one rather than clipping it, and `scripts/validate-chat-starters.mjs` and `scripts/validate-page-summaries.mjs` between them fail the build on written copy that exceeds it. A suggestion also asks about roles, never theme values: "the action colour", not the colour a theme happens to give it. A suggestion that will not fit is dropped, never truncated: half a question is not a question. The options of a question the agent asks (`QuestionCard`) are held to the same budget, for the same reason: the model is told the number through the `ask_user` input schema, `sanitizeQuestionSet` drops a question whose option outruns it, and `validate-chat-starters.mjs` holds the demo script's written options.

The design spec lives in [`design.md`](design.md) — read it before touching tokens, colors, or typography. The content style guide lives in [`content-design.md`](content-design.md) — read it before writing or editing any shipped prose (page copy, descriptions, README, release notes, microcopy).

## Registries — counts are never hardcoded

**General rule:** any count of items displayed anywhere (components, skills, tokens, releases — anything countable) must derive from a registry that is the single source of truth for that collection, kept in sync with reality by a build-time validator. Never write a literal number (or a hand-maintained list that implies one) into page copy, stats, or docs.

The full chain (`npm run validate-registry`) runs before every root build via `prebuild`/`prestorybook`/`prebuild-storybook`. The website's own `prebuild` runs a deliberate subset — the website-relevant generators and validators, skipping the library-only ones — and `website/package.json` is authoritative for which; CI and the root builds always run the full chain.

**The package barrels and exports map are generated surfaces.** `scripts/generate-library-barrel.mjs` (validate-registry chain) writes `src/index.ts` and `src/charts.ts` from `src/components/registry.json` — never hand-edit them. Modules that import recharts land in `charts.ts` automatically (recharts is an optional peer dependency; the main barrel must never force a bundler to resolve it). The `exports` field in package.json is owned by `scripts/package-manifest.mjs` (single source for the package name, version, subpaths and the init bin's `bin` entry — in-repo exports point at `./src` for workspace dogfooding, `npm run build:lib` writes the dist-form manifest that ships to npm); `scripts/validate-package-exports.mjs` fails the build if they drift (subpaths only — the bin's presence and shebang are publint's job in the package-publish lint). **The package name itself renames mechanically**: `PACKAGE_NAME` lives in `scripts/brand.mjs`, `scripts/rename-package.mjs` sweeps every specifier and install snippet from the old name to it, and `RETIRED_PACKAGE_NAMES` (same file) makes any surviving straggler a build error in `validate-package-exports.mjs` — the `PACKAGE_NAME` doc block in brand.mjs owns the rename-day recipe. `RETIRED_HOSTS` (same file, same scan) gives a domain the identical guarantee: a URL written from memory rather than derived from `SITE_URL` fails the build, which is what the 2026-09-26 move to rift-ds.com needed and did not have. The same validator holds the two hand mirrors of the author fact: the root package.json's `author` (against the dist manifest's, which brand.mjs feeds) and LICENSE's copyright holder (against `AUTHOR_NAME`) — both ship in the tarball, and the licence line had already drifted to a short form of the name nothing else used. The theme presets ship as generated CSS the same way: `scripts/generate-preset-stylesheets.mjs` writes `src/tokens/presets/` from `presetOverrides` in `website/src/lib/theme/presets.ts`, published as assets under the `./tokens/presets/*.css` subpath — never hand-edit them (see the Theme presets registry row).

**README.md is a generated surface for registry data.** `scripts/generate-readme-content.mjs` (also in the `validate-registry` chain) rewrites the marked regions below — never hand-edit inside them, and commit README.md when a build regenerates it:
- `<!-- component-count -->` and `<!-- component-list:start/end -->` — from `src/components/registry.json`
- `<!-- npm-badge:start/end -->` — the npm version badge, built from `PACKAGE_NAME` in `scripts/package-manifest.mjs`, so a scope change can never leave the badge pointing at a package that doesn't exist
- `<!-- banner:start/end -->` — the banner image link, an absolute raw URL built from `REPOSITORY_URL` in `scripts/brand.mjs` (npm does not resolve a relative image path against the repo)
- `<!-- author:start/end -->` — the author credit, built from `AUTHOR_NAME`/`AUTHOR_URL` in `scripts/brand.mjs` (see the author paragraph below)

**The author credit has one home and many derived surfaces.** `AUTHOR_NAME` and `AUTHOR_URL` in `scripts/brand.mjs` are the source; nothing else may restate either value. They reach: the site footer's bottom row and the `Person` author on both JSON-LD nodes (`website/src/lib/structuredData.ts`), the authorship sentence closing the /overview intro, the corpus's own Author section (so the site chat can answer who built it — the footer sits outside `app/`, so page-prose extraction never sees it), the published package's `author` field, the README's generated author region, the Storybook landing page, llms.txt, the MCP endpoint's browser landing page, the consumer library skill's provenance line, and every shadcn registry item's `author` (the registry-item schema's own `name <url>` form; the registry index has no author field, so it carries none). Some surfaces deliberately carry no credit: the init bin's terminal output, because content-design.md's CLI register says it never promotes; the per-component markdown pages, which are prop contracts and nothing else; and every consumer skill file other than the library skill's SKILL.md, which are procedures and reference tables.

**The README banner is a surface with no generator, and it rots.** `.github/readme-banner.jpg` is a screenshot of the site hero, so it states the brand, the install line and two counts in pixels no validator can read. On 2026-09-26 it was found still showing the old codename, the retired package name, 132 components and 8 themes, all of it wrong, and README.md ships inside the npm tarball, where that image heads the package page (the `banner` region above points at it by absolute URL, because npm resolved 1.0.0's relative path to nothing). `scripts/capture-readme-banner.mjs` re-shoots it (Playwright, dark mode, 1800x880); it is deliberately **not** a build step, on the same footing as `sync-preset-fonts.mjs` and `sync-worldmap-land.mjs` — run it by hand whenever the hero changes what it says, and commit the result. The playground's template thumbnails are the second: `website/public/images/templates/` holds one still per template per mode for the Templates view's rail, and `scripts/capture-template-thumbnails.mjs` re-shoots them on the same by-hand footing. Unlike the banner, the set is held to its list: `scripts/validate-template-thumbnails.mjs` (validate-registry chain) fails when a template in `templatesSidebarLinks` has no still or a still has no template, so only what a picture shows needs a person. Re-run it whenever a template changes what it shows.

The same script fails the build if its Tech section names a different major version of React, Next.js, Storybook, or Vite than package.json, and if **either** install surface stops mentioning the package name — `README.md` or `src/stories/Configure.mdx` (the Storybook landing page). Both tell a stranger how to install the package, and they deploy separately, so a scope rename that reaches one but not the other leaves a live install snippet pointing at a package that does not exist. **The README also ships inside the npm tarball**, so anything inaccurate there reaches every consumer — treat both files' install/usage prose as production copy. `Configure.mdx` itself is drift-protected the registry way: every countable and URL on it is a **live import** (`COMPONENT_COUNT`, `TOKEN_COUNT`, the theme order, `SITE_URL` from the brand module), it sits in `scripts/validate-doc-refs.mjs`'s sources list, and Storybook's preview applies the shipped theme presets through the same `THEME_SELECTOR_ORDER` the site's switcher reads (the toolbar's Theme control, defaulting to the served look) — so the sandbox and the site cannot describe different systems.

When a new countable collection appears on the site (a loop list, a glossary, a changelog…): create a registry file next to the collection, export the count from a small accessor module, add a validator script chained into `validate-registry`, and pull every displayed number from the export. When adding a skill: write `.claude/skills/<name>/SKILL.md` and register the name in `.claude/skills/registry.json` (`displayed` if it appears on `/skills`, `unlisted` if internal, `external` for a skill that lives outside the repo — which additionally needs its published copy at `website/src/data/external-skills/<name>.md`) — that's all. The `/skills` page is fully data-driven: it maps over `website/src/data/skills-content.generated.ts`, which `scripts/generate-skills-content.mjs` builds from the SKILL.md files in registry order, so **never hand-add a card to `website/src/app/skills/page.tsx`**. `scripts/validate-skills-registry.mjs` fails the build if a skill file and the registry drift.

**The website's /blueprints pages are a generated surface too.** `scripts/sync-blueprints.mjs` (in the `validate-registry` chain) copies the root markdown specs into `website/public/` on every build — never hand-edit those copies; edit the root files. Its `FILES` array is the authoritative list, and `scripts/validate-website-surfaces.mjs` imports it to check every synced file has a `/blueprints/<name>` page, so a spec cannot be published as a raw download with no page to read it on; the same validator holds the llms.txt route's spec-download list to `FILES` in both directions, so an unpublished spec cannot stay advertised as a link that 404s.

**The per-component markdown pages are a generated surface.** `scripts/generate-component-md.mjs` (validate-registry chain and the website's predev/prebuild) writes one `website/public/components/<slug>.md` per public component — the prop contract as markdown, served beside the live docs page (append `.md` to a component URL) — from the same `assembleComponentApi()` pass that feeds Storybook's props tables, the shipped `.d.ts` and the `get_component` tool both model-facing surfaces share. Never hand-edit the files: `scripts/validate-component-md.mjs` regenerates in memory, byte-compares, and holds the folder to the registry in both directions. The "Copy for agents" button on component pages (`website/src/components/PageLinks/CopyPageMarkdown.tsx`) and the MCP response's `markdownUrl` both point at these files.

**The shadcn registry is a generated surface.** `scripts/generate-shadcn-registry.mjs` (validate-registry chain and the website's predev/prebuild) writes `website/public/r/` — a shadcn-compatible registry, the third install path beside the npm package and the cloned repo: one item per public component with its source files embedded (the relative-import closure of its folder), a shared `base` item (the token stylesheets and their closure, the generated theme presets, the icon font's CSS, the JS motion constants, `src/behaviors/`), a `registry.json` index, and the font binaries under `assets/` (JSON cannot embed them; the site serves them instead). Two deliberate design points, owned by the generator's doc block: file targets preserve the `src/` layout under a `rift/` folder so **no import specifier is ever rewritten**, and the one rewrite that does happen is `url(*.woff2)` in the CSS copies, pointed at `${SITE_URL}/r/assets/`. Cross-component imports become absolute-URL `registryDependencies`, so items install with zero namespace configuration (`npx shadcn@latest add <SITE_URL>/r/<slug>.json`). `scripts/validate-shadcn-registry.mjs` regenerates in memory and byte-compares both directions, screens every text file with the corpus's non-sanctionable leak patterns (item files hand library source verbatim to strangers' projects), and proves closure integrity — every relative import inside every embedded file must resolve to a target some item carries. Advertised in llms.txt and on get-started; end-to-end consumption needs the deployed site (the dependency URLs bake `SITE_URL`), which is why the local proof lives in a URL-rewritten copy, not the committed files. **Fetches of the registry are counted, and it is the only place they can be**: the items are static files a CLI fetches, so analytics never sees them and the host's request logs skip them. `website/src/proxy.ts` (Next's proxy convention, matched to `/r/<item>` alone) hands each GET to `website/src/lib/registry-downloads.ts`, which adds one to a per-day Redis hash keyed by item and client family (the shadcn CLI, another script, a browser, a crawler) and stores nothing about the requester; that module's doc block owns the key shape and the fail-open rule, /privacy discloses the tally, and `npm run registry-downloads` prints it.

**The per-theme DESIGN.md files are a generated surface.** `scripts/generate-theme-design-md.mjs` (validate-registry chain and the website's predev/prebuild) writes `website/public/themes/<id>/DESIGN.md`, one per theme in `THEME_SELECTOR_ORDER`, the base look included: the theme described in the token-front-matter DESIGN.md format, purely visual (colour in both modes, type styles, radius, spacing, depth, motion), so a theme can be taken on its own. Every value is what the theme resolves to: `presetOverrides` laid over the token CSS by `scripts/token-values.mjs` (whose `layers` argument is that cascade), never restated. `/foundations/themes/<id>` renders each theme as a specimen, its header, description and shader banner drawn in the theme too, and offers the file for download, and the gallery links to it. `scripts/validate-theme-design-md.mjs` byte-compares the folder in both directions and reads every file back through the playground's importer (`website/src/lib/theme/design-md.ts`), failing when a theme's own file does not land on its own levers; a difference the format cannot carry is a row in its `SANCTIONED_DRIFT` table with the reason.

**The consumer agent skills are a generated surface.** `scripts/generate-agent-skill.mjs` (validate-registry chain and the website's predev/prebuild) writes `website/public/skill/`: one folder per row of `AGENT_SKILLS` in `scripts/brand.mjs` (the folder names are brand facts; the table is the authoritative list of which skills exist), plus `manifest.json`, which lists every skill with a one-line summary and its files. Consumers of the package install the folders into their own `.claude/skills/` so their coding agent knows the library, can restyle existing screens onto it, and can audit styles against its tokens every session. The library skill carries two references the other skills read, the component catalogue and `references/tokens.md`, every semantic token with the value it resolves to per theme and breakpoint. The token registry holds names only, so those values are read from the token CSS by `scripts/token-values.mjs`, the one resolver, which `scripts/validate-foundation-mirrors.mjs` shares the parser of. **The manifest is the one home of the file list.** The init bin (`npx rift-ds init`, source in `src/cli/`) fetches it from the live site and installs whatever it names, so a new skill or file reaches consumers on the next deploy with no package release; because the manifest is network data that decides where the bin writes, the bin checks every name and path before touching the disk. The website reads the same file through `website/src/data/agent-skills.ts`, and the get-started page's curl snippet, the llms.txt lines and the MCP `get_setup` text are all built from that accessor. Every fact derives from the registries, the token CSS, the prop JSDoc and the package manifest: the instructional prose is hand-written inside the generator, but every token and component it names passes through a lookup that fails generation on a name the registries do not hold. Props are deliberately not restated (the files point at the `.d.ts`, the per-component `.md` pages and the MCP endpoint). `scripts/validate-agent-skill.mjs` byte-compares every file in both directions (an orphan on disk fails, and the generator prunes one), holds the manifest to the table, screens the content for leaks and em dashes, and fails any of those three surfaces that spells a skill path by hand instead of deriving it; its doc block owns the full list of checks. The same generator writes **the agent starter**, `website/public/AGENTS.md` (the name is `AGENT_STARTER_FILE` in brand.mjs, after the cross-tool convention): the library skill cut to one short file a consumer saves at their project root or pastes into any agent, written to the agent (never to the person, who is told how to save it by the page around it), carrying the install and its dependencies (the peers read from the shipped manifest, the chat command from the chat registry), the setup, the rules generic React habits break, and pointers to the references, the MCP endpoint and `init` for everything else. Keep it short but complete for setup; it points rather than restates, so it never becomes a second copy of the skill. It has no page of its own: its full text opens get-started's coding-agent section in a scrollable copy frame, carried by the generated module `website/src/data/agent-starter.generated.ts`; the home hero copies the same text to the clipboard from one quiet caption-sized button (falling back to that section when the clipboard is blocked), and llms.txt links the raw file. The README offers it too, by its raw URL. The validator holds both files to the builder, each of those three site surfaces to its accessor name (`AGENT_STARTER` on the home page and get-started, `AGENT_STARTER_URL` in llms.txt), and the README to the URL the accessor builds; the corpus carries the text in its Blueprints section. This is a surface **for consumers of the package**: it is unrelated to this repo's own `.claude/skills/` and the `/skills` page, and lives under `/skill/` (singular) for exactly that reason. The style-audit skill is a consumer rewrite of this repo's `token-audit` skill, and the two are maintained separately on purpose: the repo skill leans on validators and the `ds-allow` grammar a consumer does not have.

**The site chat corpus is public-only and owner-authored-only, and both halves are security boundaries, not style choices.** `scripts/generate-site-corpus.mjs` may only read sources that are already published — page prose, the data registries, the blueprint specs. The corpus becomes the chat model's context, so anything in it can be repeated verbatim to any visitor who asks; keeping it public-only means the worst case of a successful prompt injection *out of the chat* is off-brand prose rather than a leak. The second half guards the opposite direction: text in the corpus is text the model treats as context, so third-party words — a client quote, a testimonial, a pulled-in review — would be an injection surface *into* the chat. Today every word on the site is the owner's, which is what makes the automatic page-prose extraction safe; the day a page carries third-party text, that content needs an explicit decision (and probably an exclusion) before the next build ships it to the model. The boundary is enforced as an allowlist, not remembered: a contact-shaped detail (an email address) may appear in the corpus only when a page deliberately published it through a `corpus-facts()` directive, and `scripts/validate-site-corpus.mjs` fails the build on any other route in. It still screens for the obvious slips (local paths, analytics ids, keys), but it cannot judge whether a new source was meant to be public — or whether the owner wrote it.

**Self-descriptions stay in sync.** The repo describes itself in prose in several places — `README.md`, `design.md`, this file, and the website's foundations/overview pages. Whenever a change makes a statement in any of them false (a new component category, a dropped dependency, a renamed part, a changed principle), update that prose in the same change — don't leave it for a future audit. If the drifting fact is *countable or mechanically checkable* (a count, a list, a version number), don't just fix the prose: route it through a registry + generator/validator in the `validate-registry` chain so it can never drift again (the README component section and Tech versions are the reference example).

**Prose & skill authoring rules.** The registry principle generalized: **every fact has exactly one authoritative home** — all other mentions derive from it (generated), are checked against it (validated), or point at it. Never restate a fact a registry, script, or source file already owns. Concretely:

- **Point, don't enumerate.** "The `validate-registry` entry in the root `package.json` is the authoritative list" beats a hand-copied list that goes stale.
- **Examples in skills are fictional.** Example findings use made-up component names — a factual claim about a real component inside an example rots silently.
- **No counts outside registries; no machine-local paths** — derive the repo root with `git rev-parse --show-toplevel`. The token-family sizes design.md states in words ("a four-step size scale") are held to the token files by `scripts/validate-design-counts.mjs`, whose `CLAIMS` table is the list.
- **Off-token CSS values are sanctioned at the site**, never in a skill: `/* ds-allow(<category>): <reason> */` (file-wide: `ds-allow-file`), categories owned by `scripts/validate-css-directives.mjs`. The token-audit skill reads directives; it maintains no list.
- **References are build-checked**: `scripts/validate-doc-refs.mjs` fails the build when a skill or doc references a repo path, `npm run` script, or documented API symbol that doesn't exist (the `sources` list in that script is the authoritative set of docs — the root specs, SECURITY.md, the chat eval's README and SPEC.md, and the workspace README).
- **The one content rule that is mechanically checkable is build-checked too**: `scripts/validate-shipped-prose.mjs` fails the build on an em dash in shipped copy, which `content-design.md` bans outright. It reads page prose through the same `extractProse` the corpus generator uses, so "what counts as page prose" has one definition rather than two, and its doc block owns the scope — which surfaces are in, and why agent-facing markdown, synced essays, and noindex staging pages are out. Everything else in `content-design.md` needs a reader, and stays the `content-audit` skill's job.
- **A paragraph never carries its own width cap**: design.md's Composition rule 4 constrains the column, not the content, and on a component page (the `component-doc-page` skill's rule) `scripts/validate-page-prose-width.mjs` fails the build on a pixel or character `max-width` in any `page.module.css` rule that sets paragraph type, with text that belongs to a rendered demo rather than the page sanctioned in its table.
- **A space that vanishes between source and render is build-checked**: `scripts/validate-rendered-spacing.mjs` fails on a closing inline tag butted against a word in the prerendered HTML. A space written after `</strong>` can be dropped when the text node that follows holds an HTML entity, because the transform re-chunks the node around the entity and trims the leading whitespace, so `<strong>Why so slow?</strong> Compensation` ships as one word. It reads built output rather than source, since the source pattern over-reports, which is why it runs after the website build in `verify` and in CI rather than inside `validate-registry`. The fix is always the same: use the literal character (’ “ ”) instead of the entity.

## CI & Local Verify

Every push to `main` and every PR runs `.github/workflows/ci.yml` (four jobs: library lint + build + the API compatibility gate + the package-publish lint — `scripts/validate-package-publish.mjs`, publint and arethetypeswrong over `dist/`, the resolution modes the consumer smoke never exercises, plus the rule that no shipped `.d.ts` names `@tanstack/` (TanStack Table, the engine under DataTable and the package's one runtime dependency, stays out of rift's public types) — story tests, Storybook build, and website lint + build + the checks that read or serve the finished build: the three built-HTML validators — rendered spacing, corpus coverage, and the internal-link check (`scripts/validate-internal-links.mjs` — every href in the prerendered HTML must lead to a page, route handler, public file, or redirect that exists) — then the hydration smoke, the gesture stress check and the page-level axe pass (`scripts/validate-website-a11y.mjs` — the served pages in both themes, mirroring the Storybook rule set including its settled contrast exclusion). The hydration smoke — `scripts/smoke-hydration.mjs` — serves the build and loads it in a real browser, because a green build and an HTTP 200 both held on 2026-09-06 while a hydration mismatch left every page invisible; the script's doc block owns the details, including its second life as the `ship` skill's post-deploy check against production. The gesture stress check — `scripts/validate-gestures.mjs`, over the grips in `scripts/gestures.json` — serves the same build and drags every grip under a pointer flood with the CPU throttled, because a page that renders, hydrates and passes axe can still be a trap under a real drag: on 2026-10-20 the playground's stage card blanked the whole live site when a visitor dragged its resize grip, each pointer move re-rendering the widget until React 19.2's nested-update count hit 50 and error #185 unmounted the root, and it shipped twice because no check drove a gesture. It fails on a page error, an empty body, a drag that took nothing, or more than 25 consecutive commits ending with work still pending, half React's limit, so the next regression fails in CI rather than in a visitor's browser (the Gestures row under **Registries** owns the details). The same live check is built to run on a schedule — `.github/workflows/uptime.yml` smokes production, because ISR means the served site can change with no deploy (that is how the outage appeared on a deployment that had shipped green) — and its cron runs every four hours against production. The library job ends with a **drift guard** — `git diff --exit-code` after the generators run — so a registry change that lands without its regenerated README/skills/blueprint content fails CI.

**Story tests**: `npm run test` runs every Storybook story as a render test in headless Chromium (Vitest + `@storybook/addon-vitest`, configured in `vite.config.ts`). A story that throws on render — or whose `play` assertions fail — fails the suite, so every component variant is smoke-tested on every change, and behavior a story asserts (the overlay stories' focus, Escape, and stacking checks in `Dialog.stories.tsx`) is enforced the same way. **A11y checks run alongside in `'error'` mode — an axe violation fails the suite** (see `.storybook/preview.ts`). One rule, `color-contrast`, is switched off there by the owner's settled decision; the comment beside that override is its authoritative record and the single place its details belong. Read it before touching anything contrast-related, and never re-enable the rule, restyle what it covers, or raise it as a finding without asking the owner first. Everything else in AA is enforced.

**Releases** are manual and follow the `release` skill (`.claude/skills/release`). The `Release` workflow (`.github/workflows/release.yml`, workflow_dispatch, dry-run by default) builds `dist/`, runs `scripts/smoke-consumer.mjs` (packs the tarball into two scratch Vite consumers: a plain one that builds with none of the optional peers installed, and a chat one that installs every peer, runs the packed bin's `init chat`, then `init app` and `init block` for every block, against an app-router layout, and type-checks and builds the scaffolds, with `next/link` and CSS modules declared as ambient modules since the Vite consumer does not install Next), then publishes **from `dist/`** with `npm publish --access public --provenance`. The root package.json stays `private` forever — only the generated dist manifest ships. **The version lives in three places and all must move together:** `PACKAGE_VERSION` in `scripts/package-manifest.mjs` is authoritative for what ships; the root package.json's `version` must be mirrored by hand; and `package-lock.json` records it too — refresh it with `npm install --package-lock-only` after a bump. `validate-package-exports.mjs` fails the build when any of the three disagree (a stale lockfile also dirties every fresh checkout's tree on plain `npm install`). **`rift-ds` was first published from this repo on 2026-09-26**; the release log registry (`website/src/data/release-log.json`) owns every version since, and the older versions recorded in `HISTORY.md` belong to the predecessor's scoped package. That first publish could not use OIDC at all: **a trusted publisher can only be attached to a package that already exists**, and npm says so explicitly, returning `404 ... OIDC token exchange error - package not found` from the exchange endpoint. The `bootstrap_token` input on the workflow exists for exactly that case and is off by default. Trusted Publishing was registered for this repo plus the `release.yml` filename the same day, and 1.0.1 was the first version published over OIDC with no token anywhere — which is the only proof that path works, because a dry run never authenticates and so a broken registration survives one. The predecessor's scoped package shipped 22 versions before the rename, 0.1.0 on 2026-07-26 through 0.21.0 on 2026-09-19. That log, and the build journal that ran alongside it from day one, are recorded in `HISTORY.md` at the repo root (readable in the public repository, so nothing private belongs in it). The build journal stays deliberately outside the build, the site and the corpus. The predecessor's version list is also published: `predecessorReleases` in the release log registry holds a condensed copy that /releases renders beneath the log, under its own divider, and the corpus carries. Their original homes (the old repo's release workflow header and its `/project-journal` page) were deleted with the predecessor, so `HISTORY.md` is the only full copy.

**The published API only grows.** `scripts/validate-api-compat.mjs` compares the working tree with the latest `v*` tag: every prop in the generated API (`website/src/data/component-api.generated.ts`) must survive without becoming required or losing a union member, every name an explicit export subpath exported must still be exported (types too, read from the module syntax at both revisions), every file a wildcard subpath served must still exist, and no bin may vanish. A deliberate break is a row in its `SANCTIONED_BREAKS` table with the version and the reason, and goes stale the moment that version is tagged. It runs in `verify` and CI's library job (which checks out with `fetch-depth: 0` for the tags), never in `validate-registry`: Vercel's tag-less shallow clone runs that chain before every deploy, and a missing baseline must not block the site. Outside CI a missing tag only warns; in CI it fails, so a lost `fetch-depth` cannot make the gate pass vacuously.

Two facts that bite on release day: **a published version can never be reused**, even after unpublishing, so a botched release costs a version number; and **the registry lags the workflow by minutes** — a 404 right after a green publish is propagation, not failure, so never re-run on it. Auth is **Trusted Publishing (OIDC)** — there is no npm token to expire or rotate. The registration on npmjs.com is keyed to the workflow **filename**, so renaming or moving `release.yml` breaks publishing until the registration is updated; and `permissions: id-token: write` is load-bearing for authentication, not just provenance. A dry run never authenticates, so only a real publish proves the auth path works.

`npm run verify` is the **single local mirror of CI**: lint, library build, the API compatibility gate, package build, the package-publish lint, story tests, Storybook build, website lint, website build, then the checks that need the finished build — the three validators that read built HTML (rendered spacing, corpus coverage, internal links) and the three served-site checks (the hydration smoke, the gesture stress check, then the page-level axe pass) — in that order. The rule that keeps them in sync: **when CI gains a check (a11y is the worked example), add it to `verify` in the same change** — skills and docs reference `verify`, never individual commands, so nothing else needs updating. **Three deliberate exceptions. Chromatic** (`.github/workflows/chromatic.yml`, visual regression): every run bills cloud snapshots against a monthly budget, so it is `workflow_dispatch`-only, never part of `verify`, and never a reason to treat a green `verify` as proof the pixels are unchanged. **The dependency audit**: CI's library job runs `npm audit --audit-level=high --omit=dev`, which judges the shipped dependency tree against the registry's advisory feed rather than the code, so a failure there is news from outside, not something a local run could have caught earlier. Dev-only tooling is outside the gate by a decision the workflow's own comment records: an advisory there with no upstream fix once held `main` red and skipped the lint and build steps behind it. **The drift guard**: CI's library job ends with `git diff --exit-code` after the generators run; `verify` cannot, because a local tree is dirty with the change in progress. Catching uncommitted regenerated content stays CI's job alone.

**Shipping vocabulary** — skills named for their end state, because once the Vercel project exists a push to `main` always deploys the live site (`.claude/skills/registry.json` is the authoritative list of what exists):
- **`ship`** — make it live. Full verify, merge branch work into `main` if needed, push, watch CI, then prove the deployed site renders (the hydration smoke against production — the outage class it exists for only reproduces on Vercel). Always ends deployed and verified live.
- **`super-ship`** — the bulletproof ship for structural work: run the full `drift-audit` and a scoped `api-consistency` over the components the change touched, stop at a coverage gate if any audit section was skipped or narrowed, fix the broken and stale findings, then `ship` the combined result. Higher-order — it composes the other three skills rather than restating them, and invoking it is the sanctioned way to chain an audit into a deploy. For a small change, plain `ship` is enough.
- **`checkpoint`** — save progress to a remote branch and keep working. Never touches `main`, never deploys; if invoked on `main` it moves the work to a `wip/<topic>` branch first.
- **`park`** — checkpoint, then return to a clean `main`. The branch name is the resume handle.
- **`land`** — triage all pending work at once and resolve it. Sweeps worktrees, branches, the working tree and stashes, judges each as **land / keep / delete**, merges the approved into a **local, unpushed** `main`, and verifies the combined result. Anything deleted is archived to an `archive/*` tag first, so discarding unmerged work stays reversible. Deliberately never pushes, so a batch deploy stays an explicit `ship`.

The old `merge-and-push` skill is retired because its name didn't say which of these it meant, and the vocabulary has grown since. If asked to "merge and push", confirm the intended **end state** instead of guessing: `ship` (merge into `main`, push, deploy), `checkpoint` (push the branch, keep working), or `land` (combine several pieces of pending work into a local `main`, pushing nothing).

## Token Architecture

Three tiers — **never skip a tier** (shown with the base token files' wiring; a theme re-keys the primitives and re-points the semantic layer, but the tiers never change):

```
tokens-primitives.css       --primitive-teal-08: #0E6E8F
        ↓
tokens-light/dark.css       --color-action-primary-bg: var(--primitive-teal-08)
        ↓
Component CSS               background-color: var(--color-action-primary-bg)
```

- **Primitives** (`--primitive-*`) — raw values. Source of truth. Never referenced in components.
- **Semantic tokens** (`--color-*`, `--radius-*`, `--gap-*`, `--padding-*`, `--border-*`, `--font-*`, `--motion-*`, `--icon-size-*`, `--control-height-*`, `--shadow-*`, `--layer-*` — `CATEGORY_PREFIXES` in `scripts/generate-token-registry.mjs` is the authoritative list) — always use these in components.
- **Dark mode** is driven by `data-theme="dark"` on the root element. Every semantic token has a light and dark value — no `prefers-color-scheme` queries in components.

Key invariants:
- The action colour, `--color-action-primary-bg` (split by light/dark mode by design, see design.md; which colour it is belongs to the theme), is **only** for primary CTA buttons, focus rings, active input borders, the checked or on state of a form control, the selected item of a mutually exclusive set (design.md's action selection convention — SegmentedControl's active segment, the header's current-section pill), and the hover signal of a surface that is itself a control (an expandable BentoTile's border), with design.md's one sanctioned data-viz exception: the action colour leads the chart series palette. Never decorative. Build-enforced by `scripts/validate-action-colour.mjs`: outside a focus outline, only components its `SANCTIONED` table names (each with its role) may reference `--color-action-primary-bg` or its hover and pressed steps, and charts reach it through `--color-chart-series-1`.
- Never hardcode hex values in component CSS — always a semantic token. (Deliberate off-token values are sanctioned *in place* with a `/* ds-allow(<category>): <reason> */` directive — `ds-allow-file(...)` for file-wide cases like ColorPicker's `hsl()` colour physics. Grep `ds-allow` to enumerate them; `scripts/validate-css-directives.mjs` owns the category set and build-enforces the grammar.) `scripts/validate-raw-values.mjs` build-enforces the rule itself over the stylesheets that ship in the package (`src/components`, `src/chat`): a literal colour, motion timing, font size, line height, letter spacing, font weight, or off-scale padding, margin, gap or radius fails unless a directive of its category covers it, placed in the same rule, directly above it, at the end of its line, or in the section banner (`/* ====`) it sits under. The same script holds the reduced-motion contract's one exception: a component's own `prefers-reduced-motion` query, which design.md's Motion section allows only to park a looping animation or drop an entrance, carries a `ds-allow(motion)` comment directly above it saying which.
- Never hardcode hex values in semantic colour tokens either: every `--color-*` value in `tokens-light/dark.css` must be a `var(--primitive-*)` (or `var(--color-*)`) reference — build-enforced by `scripts/validate-token-references.mjs`. This is what lets a consumer override a primitive and have it cascade through the whole system. (The same script holds the places colour values live outside CSS to their tokens: the chart palette's SSR fallbacks in `src/components/Chart/palette.ts` to the `--color-chart-series-*` tokens, every `getCSSVar('--color-…', '<fallback>')` literal in `src/components` to its token's light-theme resolution, the playground's `NEUTRALS` mirror in `website/src/lib/theme/theme-overrides.ts` (the shared theme levers, imported by the playground and the design-system landing page) to the neutral primitives, and the share card's `BLOB_HEX` mirror in `website/src/lib/ogImage.tsx` to the ambient background's blob tokens — the named mirrors in both directions, so a retuned neutral, series, or blob colour cannot ship without every mirror moving with it.) `scripts/validate-theme-mirrors.mjs` extends the same guarantee to every remaining hand mirror of token data: the playground's `CHROMATIC_RAMPS`, `ACTION_COLOR_PRESETS`, `ACTION_SEMANTIC_REFS` and `RADIUS_STEPS` tables, the feel levers' ladder tables (density, type scale, and the motion lever's `MOTION_DURATION_STEPS`, which must cover every duration a theme paces), the weight and tracking levers' `TYPE_STYLES` table (held to the type styles' weight and letter-spacing tokens in both directions), the icon levers' `SHIPPED_ICON_WEIGHT`/`SHIPPED_ICON_FILL` (held to the fallbacks in `src/fonts/material-symbols.css`), every `motion.ts` constant whose doc comment says it mirrors a `--motion-duration-*` token, every `var()` name in `presets.ts`, InspectMode's prefix strings (held to the exported `CATEGORY_PREFIXES`), the spatial page's swatch rows, and every token name `design.md` mentions — a token rename that misses any of them fails the build. `scripts/validate-foundation-mirrors.mjs` covers the foundations pages that script does not: every value a page prints beside a swatch (the motion durations and easings, the two shadows per theme, the primitive hexes with their RGB captions, each colour swatch's per-theme primitive and value, and each type style's size, weight, leading and tracking with its 768px step) is held to the token CSS, because the swatch renders the live property and so follows a retune while the caption beside it would not.
- Every `var(--…)` a component references must actually resolve: `scripts/validate-token-usage.mjs` fails the build on a reference to a custom property nothing defines (a fallback value marks a deliberate consumer-override hook and is exempt). This is the guard that would have caught Dialog styling its title with a token family that never existed.
- Buttons are always `--radius-pill`. Inputs are always `--radius-300`. (The token is the rule; its value is the theme's, and a squared theme takes the pill down onto the radius scale.) Sanctioned departures: Card/EntityCard navigation tiles and the chat's bubbles and card furniture use `--radius-600` — design.md's Border Radius Scale owns the full list — and the chat Composer's input shell holds its own component-local `--ds-composer-radius`, computed concentric with its send button from the live radius tokens (29px in the base theme — the geometry is specified in design.md's Composer section).
- Timings that live in JavaScript timers (hover show/hide delays, toast auto-dismiss, carousel autoplay, feedback resets, scroll settle, the streaming reveal's rate floor and drain window…) have one home too: the shared constants in `src/tokens/motion.ts`, published as `rift-ds/tokens/motion`. Never write a literal ms value into a component timer — import the constant, or add one there deliberately; `scripts/validate-js-timings.mjs` fails the build on a literal timer delay or a `*_MS` constant outside `motion.ts`, with network timeouts sanctioned in its table. Most are schedule timings the reduced-motion guard deliberately ignores; a constant that paces an animation must be guarded by its component in JS (design.md's Motion section owns the contract and the exceptions).
- Breakpoints have the same shape of home: `src/tokens/breakpoints.ts` (published as `rift-ds/tokens/breakpoints`) holds the library's set and the `mediaBelow`/`mediaAbove` query builders, and `website/src/config/breakpoints.ts` holds the site-only families. CSS cannot read a variable in an `@media` condition, so stylesheets keep the literal, and `scripts/validate-breakpoints.mjs` holds every `@media` width and every media-query string in TypeScript to the set: a width outside it needs a `/* ds-allow(breakpoint): <reason> */` directive directly above the query. JS never writes a query string by hand; it builds one from the module, and the validator fails on a spelled-out query in TypeScript (even one whose width is in the set) unless a `ds-allow(breakpoint)` comment above it says why. What each step does lives beside its constant as data (`BREAKPOINTS`, `SITE_BREAKPOINTS`), which `/foundations/layout` renders and the validator holds to the constants in both directions, so a new breakpoint is documented on the site by existing. design.md's Responsive Behavior → Breakpoints owns the conventions.
- Stacking is a token category: every z-index of 10 or more names a `--layer-*` token (the library's, in `tokens-light.css`, declared lowest to highest with what sits on each layer in a trailing comment) or, in the site, a `--layer-site-*` token from `globals.css`; a larger number that is still local order inside one component takes a `/* ds-allow(stacking): <reason> */` directive directly above it. `scripts/validate-stacking.mjs` enforces all of it, and `/foundations/layout` renders both ladders from the stylesheets. design.md's Elevation & Depth → Stacking owns the roles.

## Component Anatomy

Every component lives in its own folder under `src/components/`:

```
src/components/Button/
├── Button.tsx            # TypeScript implementation + exported interface
├── Button.css            # Scoped CSS using semantic token vars
└── Button.stories.ts     # Storybook stories (Meta + named Story exports)
```

Three sanctioned exceptions to self-containment. Every link-rendering component reads its link component from `src/behaviors/LinkProvider.tsx` (design.md's "Links go through the app's router" paragraph owns the contract). Every component that hides text imports the one `ds-visually-hidden` class from `src/behaviors/visually-hidden.css`. And every overlay imports the shared behavior hooks from `src/behaviors/` rather than hand-rolling its own document listeners. The modal overlays (Dialog, AlertDialog, Drawer, CommandPalette, Lightbox, AttachmentViewer, BentoTile's overlay, and AppSidebar's mobile drawer) take the dismissal stack, focus scope and scroll lock (see **Project Structure**); the non-modal ones (every other component importing `useLayer`: the popovers, menus, pickers and tooltips, and the rest of the roster `/foundations/accessibility` prints from that import) take the dismissal stack with light dismiss, and are placed against their control by `src/behaviors/useAnchoredPosition.ts`; and Toolbar reads the shared focusable query for its keyboard model. design.md's Components intro owns the contract. `scripts/validate-overlay-listeners.mjs` build-enforces it: a document or window key or press listener anywhere in `src/components` or `src/chat` fails the build unless its table sanctions it with a reason (CommandPalette's Cmd+K and the two arrow-key galleries today). A component that handles Escape in its own keydown handler marks it handled with `event.preventDefault()`, which the stack respects, so closing a list never also closes the Dialog around it.

**Shared primitives are drawn once, and surfaces belong to families.** The small things many components need have exactly one drawing each, exported beside the control that owns it and composed everywhere else: the three form-control indicators (`CheckboxIndicator`, `RadioIndicator`, `SwitchIndicator`, presentational companions of Checkbox, RadioButton and ToggleSwitch, their states keyed on their own modifier classes, lit on hover through the `ds-control-host` class a host puts on its interactive root), the one SVG check and minus (`CheckIcon` and `MinusIcon`, exported beside Checkbox), the chosen mark (`ChosenMark`, from the Dropdown module, the trailing check every listbox and menu row shows on its selected item), the `ds-visually-hidden` class in `src/behaviors/visually-hidden.css`, CircularButton as every header's close, and SegmentedControl as every mutually exclusive set of pills. A host that is itself the control (SelectionCard, QuestionCard, InspectorToggleSwitch's bar, FilterBar's multi-select rows) draws the indicator and carries the role and state on its own root; nothing redraws a box, a circle, a track or a check. The same shape of rule holds the surfaces: a component takes its family's fill, border, radius, hover, selected and disabled treatment (a choice offered as a row wears Input's surface, a card that holds content the container surface, an overlay row the passive hover at `--radius-200`, a navigation list's current item the passive active token), and a departure is a sentence in the component's design.md spec. design.md's Components intro owns both lists ("Shared primitives, never redrawn" and "Surfaces by family"). `scripts/validate-shared-primitives.mjs` build-enforces the primitives: a font glyph standing in for a control, an indicator class written outside its owner, a copied control part or per-component check rule, a second visually-hidden recipe, a self-drawn close button or a hand-built radiogroup fails the build unless its `SANCTIONED` table records the departure with a reason (and a stale entry fails too). What the validator cannot see, a surface outside its family's convention, is the `component-consistency-audit` skill's review, which the `new-component` and `design-qa` skills both call. The 2026-10-23 audit that produced all of this had found the same control drawn four ways and seven surface families each split on fill, hover or radius, every one of them green in CI.

Components are imported in the website through the package's public exports (deep subpaths; the barrel `import { Button } from 'rift-ds'` also works):
```tsx
import { Button } from 'rift-ds/components/Button/Button';
```

CSS class naming: `ds-{component}` base class, `ds-{component}--{modifier}` for variants. Example: `ds-button`, `ds-button--primary`, `ds-button--compact`. `scripts/validate-class-names.mjs` holds every registered component to its expected base class; its `SANCTIONED` table records the departures (the Chart/ set's shared `ds-chart` card, and the older run-together names such as `ds-colorpicker`, kept because a consumer may target them).

**The props interface is a published contract.** Since `rift-ds` ships to npm, every component follows one API shape — full details and code in the `new-component` skill; `Button.tsx` (button-or-anchor) and `Input.tsx` (form control) are the reference implementations. The mechanical half is build-enforced by `scripts/validate-component-contract.mjs` (a ref taken through forwardRef with a displayName or as a plain prop, props extending the native element's, and the ref and the rest spread on one node with the root class after the spread, read from each component's syntax; a deliberate departure, PinInput's ref on its first cell, is sanctioned in its table with the reason), and the runtime half by the props-contract story in `src/stories/Contract.stories.tsx`, which renders every component with a ref and a `data-testid` and fails unless both reach the same element, and fails on any registered component it cannot render (its stories' meta must name the component, or the story needs a fixture). The library reached full conformance on 2026-10-21; the `api-consistency` skill audits what neither can see (naming, vocabulary, descriptions):

- `'use client'` on the first line **only** when the component uses hooks, handlers, or browser APIs. Presentational components (e.g. `Table`) deliberately omit it so consumers can render them from a Server Component.
- Own props as a `type`, then `export interface XProps extends XOwnProps, Omit<React.ComponentPropsWithoutRef<'el'>, keyof XOwnProps> {}` — so native attributes pass through.
- A ref onto the primary node (the **panel** for portal components like Dialog/Drawer). New components take it as React 19's plain `ref` prop on a named function component, with props built on `ComponentPropsWithRef`; the existing ones use `React.forwardRef` plus `displayName`, which stays valid and is not migrated, since a consumer cannot tell the two apart. Merge with any internal ref rather than replacing it.
- `{...rest}` spread onto that node before the component's own attributes, so those win; a consumer-overridable default (a landmark's `aria-label`) goes before the spread instead, so a passed value wins.
- Native event signatures keep the standard names. `onChange` is a `ChangeEventHandler`; the convenience callback is named for the value's shape — `onValueChange` (string/number), `onCheckedChange` (boolean), `onValuesChange` (array) — and both fire.
- **State a consumer can own follows the controlled/uncontrolled pair convention**: `x` (controlled), `defaultX` (the uncontrolled start), and `onXChange`; when the state is the component's value the names are `value`/`defaultValue`/`onValueChange` (booleans `checked`/`defaultChecked`/`onCheckedChange`, arrays `values`/`defaultValues`/`onValuesChange`, open state `open`/`defaultOpen`/`onOpenChange`). With `x` undefined the component keeps its own state, seeded from `defaultX`. A component that is fully controlled by design (it renders state the host owns, such as ThreadPanel) says so in its design.md spec. `scripts/validate-prop-vocabulary.mjs` build-enforces the pair: a prop with a change callback and no `default*` partner fails, unless the component is native-backed (an `<input>`, `<textarea>` or `<select>`, whose own `defaultValue` already reaches the element) or recorded in its `SANCTIONED_CONTROLLED_ONLY` table with the reason.
- **A literal English string is a prop, announced or visible.** An `aria-label` or visually hidden text the component writes itself (a close button's name, a region's label) is an optional `*Label` prop whose default is the English text (a function when the text interpolates a value, `removeLabel(tag)`), so a consumer can localise every name the component announces. `scripts/validate-accessible-names.mjs` fails the build on a literal `aria-label`, `aria-roledescription` or `ariaLabel` in `src/components` or `src/chat`, unless the element spreads the rest props after it (then the consumer's native attribute already overrides it) or its table sanctions it (the scripted demo's own copy). The same holds for the words on screen: a "Loading…", a "Today" marker or a weekday header is a prop with the English text as its default (an array for a list of names), and `scripts/validate-visible-text.mjs` fails the build on literal JSX text, exempting icon ligatures, the doc-only helpers (the registry's `docOnlyHelpers`) and the scripted chat demo. Text inside string literals and arrays cannot be told from code by syntax, so the `api-consistency` skill reviews it.
- `variant` not `priority`/`kind`; `disabled` as a real boolean. **Figma variant properties are not code props** — `hover`/`active` are CSS pseudo-classes, not state a consumer sets.
- **`variant` is emphasis, `tone` is colour.** Emphasis values (`primary`/`secondary`/`tertiary`) ride `variant`; colour rides `tone` (`default`/`neutral`/`destructive`), so one prop never mixes the two axes. Status-bearing components keep the five status roles on `variant`. A data entry (a menu item, a command row) marks danger with `destructive?: boolean`, not a `tone`. A value that moves to the other axis stays on the old one as a `@deprecated` alias that renders unchanged. design.md's Components intro owns the details. `scripts/validate-prop-vocabulary.mjs` build-enforces the mechanical half: no union mixes the axes, `tone` speaks the colour vocabulary (sanctioned exceptions in its table), and no code in `src/` or `website/src/` outside a component's own folder passes it a deprecated prop or a legacy value, so a deprecation is migrated in the same change that makes it. The same script holds `size` to the density pair (`default`/`compact`) and a `variant` outside emphasis and the status roles to a recorded form, each departure sanctioned in a table (`SANCTIONED_SIZES`, `SANCTIONED_FORM_VARIANTS`).
- **A link goes through the link component, never a raw `<a href>`**, so a consumer's router reaches it: an optional `linkComponent` prop, resolved with `useLinkComponent(linkComponent)` from `src/behaviors/LinkProvider.tsx` in a client component (prop, else the nearest `LinkProvider`, else `<a>`) or `linkComponent ?? 'a'` in a server-renderable one, which cannot read context. Build-enforced by `validate-component-contract.mjs`, whose `SANCTIONED_ANCHORS` table holds the deliberate raw anchors (AnchorNav's in-page jumps); design.md's Components intro owns the contract.
- Deprecate, never remove. `scripts/validate-api-compat.mjs` holds it against the last published version (see **CI & Local Verify**). Document intentional native-name collisions (`size`, `title`) in the prop's JSDoc.

**Prop documentation is build-enforced.** Every own prop needs a JSDoc description: it is the single source for Storybook's props tables and for the `.d.ts` that ships to consumers, and `scripts/validate-prop-docs.mjs` fails the build on a prop without one. The same script fails when a component whose props type declares members comes back from the parse with none, which is the failure a description check passes straight through, and when an own prop takes a native attribute's or DOM event's name with a different meaning (`title` as a heading, `onSelect` taking an item) without a JSDoc saying it replaces the native one. Three rules follow from how that pipeline works:

- **Never put a prop description in a story's `argTypes`.** `argTypes` entries override docgen, so a description there shadows the JSDoc and silently drifts from it. Stories set `control` and `options`; the source owns the words.
- **A re-export in a component file goes below the component.** In a file with one component, the parser names every export after it and keeps the first it meets, so `export { helper } from './x'` or `export type { T } from './x'` written above the component takes its name and leaves the props table empty. `ShaderField.tsx` and `AttachmentGroup.tsx` are the worked examples; `export *` also avoids it, but widens the public API to whatever the module exports later.
- **On a deprecated prop, put a sentence *before* the `@deprecated` tag.** The docgen parser moves the tag and everything after it into a separate `tags` field, so a prop documented *only* with the tag has an empty description and renders as a blank cell. `` /** Legacy alias for `variant`. @deprecated Use `variant` instead. */ `` keeps both.

The parser settings in `.storybook/main.ts` and in `validate-prop-docs.mjs` are deliberately identical, and both load the one patch the parser needs (`scripts/docgen-scoped-defaults.mjs`, which reads each component's defaults from its own declaration rather than every sibling's in the file), so the validator sees exactly what the rendered table sees. The shared module then drops what is not a component: the parser documents every export of a file, so a helper, hook or type re-exported from a component module would otherwise be served as a component with no props (`isComponentDoc` in `scripts/component-docgen.mjs` owns the test). Two of them are load-bearing and easy to break: `tsconfigPath` must point at `tsconfig.app.json`, because the root `tsconfig.json` is solution-style (`"files": []` plus references) and yields a program containing no files; and the parser must be `react-docgen-typescript`, because plain `react-docgen` finds no component at all in one that returns `createPortal(...)` with no direct JSX (AlertDialog, CommandPalette).

## How to Add a New Component

A new component is not done until it appears in **every** place the system documents itself: the library, Storybook, and all relevant sections of the showcase website. Do not skip registration steps.

1. **Create the folder**: `src/components/MyComponent/`
2. **Write `MyComponent.tsx`**: Export a named component + a TypeScript interface for props, following the published-contract shape in **Component Anatomy** above (`'use client'` when interactive, own-props split, a ref on the primary node, `{...rest}` spread, native event signatures). Use semantic tokens in class names, never inline styles.
3. **Write `MyComponent.css`**: All CSS vars must be from `tokens-light/dark.css`. No hardcoded hex, px values from primitives, or magic numbers.
4. **Write `MyComponent.stories.tsx`**: Export a `meta` (with `title: 'Components/MyComponent'`, `tags: ['autodocs']`) and at least a `Default` story plus one per meaningful variant. (`.stories.ts` also works for stories with no JSX, but `.tsx` is the convention across the library.)
5. **Add a website showcase page**: Create `website/src/app/components/my-component/page.tsx` + `page.module.css` + `layout.tsx`. Follow the pattern in an existing page (e.g., `website/src/app/components/button/page.tsx`). The `layout.tsx` must be exactly `export const metadata = componentPageMetadata("my-component");` — title *and* description come from the registry, so the description lives in one place. A slug with no registry entry fails the website build.
6. **Register it** — one entry, and most surfaces follow automatically:
   - `src/components/registry.json` — add an object to `components` (alphabetical by `name`) with `name`, `label`, `slug`, `description`, `category` and `client`. **The sidebar nav entry, the sitemap, the breadcrumbs, the mega-nav and the page's title/description all derive from this** — do not hand-add a nav entry.
   - `website/src/components/ComponentPreviews/ComponentPreviews.tsx` — add a preview entry under the component's slug. This is the one surface still hand-maintained, because each preview is a bespoke miniature; the index's category section and the sidebar accordion both derive from the registry.
7. **Document it in `design.md`**: add a short component spec section (class name, tokens used, key behaviours).

Steps 5–7 are build-enforced by two validators: `scripts/validate-website-surfaces.mjs` fails the build if any public component is missing its showcase page, preview entry, or `design.md` spec (the nav entry and its order are derived from the registry, so they cannot drift); `scripts/validate-page-titles.mjs` fails it if the page has no `layout.tsx`, or if that layout does not derive its title via `componentPageMetadata("<slug>")`.

Checklist before shipping a component:
- [ ] Props follow the published-contract shape (own-props split, a ref on the primary node, `{...rest}`, native event signatures); the ref and rest shape is build-enforced by `validate-component-contract.mjs` and the props-contract story
- [ ] Any link renders through the link component (`linkComponent` prop; `useLinkComponent` when the component is client-rendered), never a raw `<a href>` (build-enforced)
- [ ] State a consumer can own follows the controlled/uncontrolled pair (`x`/`defaultX`/`onXChange`), or design.md says it is controlled by design (build-enforced)
- [ ] Every English string it writes, announced or visible, is a prop with the English text as its default (build-enforced for attributes and JSX text; strings in literals and arrays are a review item)
- [ ] An overlay dismisses through `useLayer`, and an Escape handled in its own keydown calls `preventDefault()` (build-enforced for document listeners)
- [ ] Composes the shared primitives rather than redrawing one: the control indicators, `ChosenMark`, `ds-visually-hidden`, CircularButton for a close, SegmentedControl for an exclusive set (build-enforced by `validate-shared-primitives.mjs`); and takes its surface family's fill, border, radius, hover, selected and disabled tokens (the `component-consistency-audit` skill's review)

## How to Add a New Token

Tokens also have multiple homes — a token that exists only in CSS is incomplete. When adding or changing a token:

1. **The file follows the category** (`SEMANTIC_FILES` in `scripts/generate-token-registry.mjs` is the authoritative list of what the registry reads): colour tokens go in `src/tokens/tokens-light.css` **and** `src/tokens/tokens-dark.css` (light/dark parity is build-enforced by `scripts/validate-token-registry.mjs`); spacing, radius, border, icon-size and control-height tokens in `tokens-light.css` alone (a control-height step is also a row of `CONTROL_HEIGHT_STEPS` in `website/src/lib/theme/theme-overrides.ts`, which the density lever scales and `scripts/validate-theme-mirrors.mjs` holds to the primitives); shadow tokens in **both** theme files (the elevation values differ per theme, and colour parity enforcement does not cover them — a shadow added to the light file alone ships silently unchanged in dark mode); typography in `tokens-typography.css` (a new type style also needs a row in `TYPE_STYLES` in `website/src/lib/theme/theme-overrides.ts`, which `scripts/validate-theme-mirrors.mjs` holds to the CSS); motion in `tokens-motion.css`. Only colour and shadow are theme-split — `tokens-dark.css` carries nothing else, and a duplicate there is dead weight the build never notices. Add a primitive to `tokens-primitives.css` first if no suitable one exists; semantic colour tokens **must** reference primitives via `var()` (build-enforced by `scripts/validate-token-references.mjs`).
2. **Document it in `design.md`**: it's the source of truth for the design language — record the token's role and how it relates to its neighbours, never its colour value (design.md is theme-agnostic; the base values live in the token files and on `/foundations/colour-mode`).
3. **Add it to the foundations doc pages** on the website, in the section matching its type (the values these pages print are build-checked against the token CSS by `scripts/validate-foundation-mirrors.mjs` and, for the spatial page, `scripts/validate-theme-mirrors.mjs`, so type what the token resolves to):
   - Semantic colors → `website/src/app/foundations/colour-mode/page.tsx` (add a swatch data entry with per-theme primitive name/hex/RGB, and a new `SectionTitle` group if it's a new category). **Every colour token needs a swatch — this is build-enforced**, in both directions, by `scripts/validate-website-surfaces.mjs`: the page states it shows all of them and prints the count from `TOKEN_COUNTS`, so a token with no swatch would turn that sentence into a lie. Skipping a niche internal role is no longer an option
   - New primitives → `website/src/app/foundations/colour-primitives/page.tsx`
   - Spacing/radius/border/control height → `website/src/app/foundations/spatial/page.tsx`
   - Shadows/depth → `website/src/app/foundations/elevation/page.tsx`
   - Typography → a type style is a row in `website/src/app/foundations/typography/TypographyView.tsx` (the page's client view; its captions are held by `scripts/validate-foundation-mirrors.mjs`); a new `--font-size-*` or `--font-line-height-*` ladder step needs nothing, because the page's server shell (`page.tsx`) reads the ladders from `tokens-typography.css` into its Scale ladders table
   - Icon sizes → `website/src/app/foundations/icons/page.tsx` (the `--icon-size-*` scale table)
   - Motion (durations/easings) → `website/src/app/foundations/motion/page.tsx` (add a `MotionSwatch` entry to the matching token array)
   - Stacking (`--layer-*`) → nothing to add: `/foundations/layout` reads the layers and their trailing comments straight from `tokens-light.css`, so write the comment (`scripts/validate-stacking.mjs` requires one)
4. **Update the Storybook token docs**: `src/stories/Tokens.stories.tsx` documents tokens by category (primitives, colours, status, chart, elevation, spacing, motion, stacking) — add the new token to the matching story, or a new story if it's a new category. (`src/stories/` also holds `Typography`, `Icons`, and `Logos` foundation docs.)
5. **Counts take care of themselves**: `src/tokens/registry.json` is regenerated from the token CSS on every build (see **Registries**), so displayed token counts update automatically — never hardcode one. If the token introduces a *new prefix*, generation fails until you add the prefix to `CATEGORY_PREFIXES` in `scripts/generate-token-registry.mjs` and give the category a home wherever counts are shown.

## Design Principles

These are stated at the level of **token roles**, deliberately: which colour, radius, typeface, or shadow a role resolves to is the theme owner's decision, lives in the token files and the preset registry (`THEME_PRESETS`), and can change without any of these sentences becoming false.

- **One face per family role, one weight per tier**: levels within a tier share a weight and step by size unless a preset deliberately specialises one style through its extras (Forest and Zest set Sub Display a step under their display tier), and which weight each tier carries is the theme's call, the same as the faces. The base theme carries heading hierarchy by weight contrast (a light display tier over a bold heading tier); a theme may move, invert, or close that gap. The type scale chains through two family roles (`--font-family-heading` / `--font-family-body`), both resolving to `--font-family-primary` by default, so a theme or consumer can split heading and body faces without touching the principle (design.md's Font Family section owns the split).
- **The primary-action token is reserved for actions**: primary CTAs, focus rings, active input borders, the checked or on state of a form control, the selected item of a mutually exclusive set, and the hover signal of a surface that is itself a control. Never decorative, or it stops meaning "click here".
- **Shape is a per-element-type token, never a per-instance choice**: all buttons share one radius role, all inputs another. Change the token, not the component.
- **Five status roles** (`info`, `positive`, `warning`, `error`, `neutral`), shared by every status-bearing component through the same `--color-status-*` set.
- **Depth is token-owned**: surfaces separate from the page by contrast through the container ramp (lighter or deeper is the theme's call), and the only shadows are the elevation tokens the system defines. Components never add their own.
- **Platform fidelity is the one sanctioned departure** from the type and depth rules above: the iOS and Android variants of the mobile navigation components restate each platform's face, metrics and material under the `platform` directive category, so a mock reads as the real system chrome (design.md's BottomNav spec owns the exception).
- **Icons sit on the `--icon-size-*` scale** — set the scale variable, never `font-size` on an icon.
- **Every AI chat follows the chat widget's responsive pattern**: docked beside the page at `DOCK_QUERY`, a modal overlay below it, a full-viewport takeover at `TAKEOVER_QUERY` — the package's `ChatLauncher` (`src/chat/ChatLauncher.tsx`, which the site mounts through `SiteChatMount`) is the reference implementation, and any other chat surface (a template's `TemplateAssistant`, the chat home, the next one) reuses those thresholds (`src/chat/queries.ts`) and that behaviour rather than inventing its own. A host reserves the panel's width only at the dock threshold, never below it, or the page squeezes to a sliver beside the chat. Placement is an option on top of the pattern, not a fourth threshold: the header's Chat position menu lets the visitor dock the panel to either edge or float it as a card they move and size (`src/chat/placement.ts` owns the roster and the shared limits; the site panel and the playground stage are the two hosts that offer it). design.md's ChatWidget spec owns the rule, the placement contract, and the two exceptions (a panel seated inside a frame of its own, and a chat that is the whole page).
- **File-format colours are fixed, not themed**: the four `--color-file-*` roles point at the `--primitive-file-*` values each format is known by, the same in every preset and both modes, because recognition is their whole job. They only ever fill an attachment's type mark, and nothing is read against them: the mark's lettering is drawn in a text colour (design.md's File type section owns the rule).
- **Tables are one family, drawn from one set of tokens**: every table (the library `Table`, plain or `bordered`, `DataTable`, `Prose`'s markdown tables, and the site's blueprints tables through `website/src/components/MarkdownTable/`) reads its colours from the `--color-table-*` family, so a docs table and a product table are drawn alike, and `scripts/validate-table-styles.mjs` fails the build when any other stylesheet colours a table part or a drawing file colours one outside the family (design.md's Table surfaces section owns the roles). On a doc page, reach for `Table` with `bordered` (or markdown through `MarkdownTable`) rather than writing table CSS.
